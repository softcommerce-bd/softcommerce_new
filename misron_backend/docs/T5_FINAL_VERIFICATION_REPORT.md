## 3. `BankTransaction::generateTransactionNo()` (investigation)
* **Call sites (4), all in `app/Http/Controllers/BankTransactionController.php`:** line 61 `deposit` ('deposit'), line 126 `withdraw` ('withdraw'), line 192 `transfer` ('transfer'), line 250 `chequeClearing` ('cheque_clearing'); each is the `transaction_no` argument of `BankTransaction::create([...])` inside `DB::beginTransaction()/try`.
* **Definition:** none. `app/Models/BankTransaction.php` is an empty model (`use HasFactory` only); `git log -S generateTransactionNo` finds only the initial import commit; no trait, no helper, no vendor class defines it. Every call therefore throws `Error: Call to undefined method` and the screen answers "Error processing ...". Result: **bank deposit, withdraw, transfer and cheque clearing cannot succeed in this repository.**
* **Table:** `bank_transactions` exists in all local schemas but its CREATE statement is **not in the repository** (no migration, no `sqlupdates` file). Columns: `id, transaction_no, type, from_account_id, to_account_id, amount, transaction_date, cheque_no, cheque_date, clearing_date, status, description, reference, voucher_id, created_by, created_at, updated_at, deleted_at`. `transaction_no` has a **unique** index (`bank_transactions_transaction_no_unique`). The table is empty in every local database (including the staging copy), so there is no existing number to infer a format from.
* **Conventions elsewhere (not authoritative for this document):** `BalanceTransfer` uses `WD/DP/TR/CO/AD-YYMMNNNN` per type; `ExpensePayment` `EXP-YYNNNNNN`; `Income` `INC-YYNNNNNN`; `Voucher` `CP/BP/CR/BR/JV/CV-YYMMNNNN`; `SupplierPayment` `PAY-NNNNNN`; `CustomerPayment` `CUS000001`; all are "latest row + 1" (now read under a row lock). A separate table `account_transfers` with unique `transfer_no` exists and no code uses it. The view `bank_operations.blade.php` only prints `transaction_no`.
* **Uniqueness / concurrency / transaction needs (technical, independent of the format):** unique column; must be generated inside the creating transaction (the four calls are); must use the same locking-read pattern now used by the sibling generators so simultaneous requests get consecutive numbers; a deleted row keeps its number (soft delete column exists, so read with trashed rows).
* **Decision:** the format is **not established by authoritative code or an approved decision**, so the method was **not implemented** and no format was invented. The required decision is in the register (decision B-1): the string format per type (`deposit`, `withdraw`, `transfer`, `cheque_clearing`), the period reset, and whether these screens are in use at all (the bank operations may be intended to go through `BalanceTransferController` instead). Once approved, implementing it and adding the tests is a short change; the retry tests for the four actions already have a scenario template.
